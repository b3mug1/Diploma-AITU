# Архитектура и диаграммы

## Архитектурное описание

Предварительно система разделена на React SPA, REST API на FastAPI и PostgreSQL. Клиент обращается к API по HTTPS; API проверяет роль пользователя, выполняет распределение по версионируемому набору утверждённых правил и сохраняет результат в транзакции. Модуль ремонта управляет заявками и переходами статусов. WebSocket используется для доставки обновлений dashboard и статусов заявок. Nginx обслуживает frontend. Конкретный механизм аутентификации, хранения токена, срок хранения аудита и конфигурация развертывания требуют уточнения до реализации.

## Сущности данных (предварительно)

- **User** — учетная запись и роль; связь со Student необязательна.
- **Student** — учебный идентификатор, имя/группа и другие минимально необходимые атрибуты.
- **Locker** — номер, местоположение, характеристики, состояние.
- **Assignment** — студент, шкафчик, даты назначения/освобождения, создавший пользователь.
- **RepairTicket** — автор (студент), шкафчик, описание/категория проблемы, ответственный техник, статус, временные отметки и итог.
- **AllocationRun** (если требуется воспроизводимый пакетный процесс) — версия правила, дата запуска, минимально необходимые входные данные и результат распределения; не сохранять избыточные чувствительные атрибуты.
- При необходимости **AuditEvent** — действие, субъект, объект, время и минимальные метаданные.

Ограничения целостности (например, максимум одно активное назначение на шкафчик) должны обеспечиваться на сервере и, где возможно, базой данных. Распределение с приоритетами должно быть объяснимым и проверяемым человеком; в текущем scope это детерминированное бизнес-правило, а не ML. Социальный статус, GPA и активность могут быть персональными/чувствительными данными: не собирать их без подтверждённой необходимости, основания и строгого контроля доступа. Предпочтительнее передавать системе минимальный флаг допустимости приоритета вместо подробной причины, если это согласовано с университетом.

Для ремонта предполагаемые переходы: `submitted → assigned → in_progress → awaiting_admin_confirmation → closed`; возврат на доработку должен сохранять причину и историю. Студент видит только свои заявки, техник — назначенные ему, администратор — все в пределах полномочий.

## Согласование с требованиями

Use cases должны соответствовать FR-03–FR-17. Диаграммы являются черновыми: финализировать их после интервью и решения о правилах назначения, доступах, статусах ремонта и системных интеграциях.
