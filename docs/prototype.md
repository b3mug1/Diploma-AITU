# Прототип ключевых сценариев

Прототип на этом этапе описан как экранные наброски и потоки; визуальные макеты/ссылка на Figma ещё должны быть добавлены. Макеты следует проверить с пользователями до фиксации UI.

## Сценарий администратора: назначение

1. Вход → административный dashboard (показатели: всего, доступно, занято, обслуживание).
2. Раздел «Студенты» → поиск по barcode/имени/группе → карточка студента.
3. «Назначить шкафчик» → список только доступных шкафчиков с номером, размером, этажом.
4. Подтверждение → показать результат, дату, статус; обновить dashboard.
5. При конфликте показать понятную ошибку и не создавать второе активное назначение.

## Сценарий администратора: обслуживание

Список шкафчиков → открыть шкафчик → изменить статус на maintenance → система предупреждает о существующем активном назначении и требует определить дальнейшее действие → сохранить изменение с автором/временем.

## Сценарий студента

Вход → страница «Мой шкафчик» → номер, местоположение, статус и срок (если сроки будут определены). Если назначения нет — ясное сообщение и указание дальнейшего действия; пользователь не видит чужие назначения.

## Сценарий студента: заявка на ремонт

«Мой шкафчик» → «Сообщить о проблеме» → выбрать тип проблемы и описать её → отправить → получить номер заявки и статус. В разделе «Мои обращения» студент видит статус, дату обновления и решение; подробности чужих заявок недоступны.

## Сценарий администратора и техника: ремонт

Администратор открывает очередь новых заявок → проверяет шкафчик и описание → назначает техника. Техник открывает свою очередь → фиксирует начало/результат работ → передаёт заявку на подтверждение. Администратор подтверждает и закрывает заявку либо возвращает её технику с комментарием. После закрытия студент получает уведомление.

## Сценарий автоматического распределения

Администратор запускает распределение после проверки списка студентов и свободных шкафчиков → система применяет утверждённые правила приоритета → показывает список результатов с объяснением критерия и нераспределённых студентов → администратор просматривает и подтверждает публикацию. Нужны согласованные tie-breaker, апелляция и возможность корректировки с записью причины. До согласования правил и обработки данных этот сценарий является макетом, а не утверждённой политикой.

## Пример API (предварительный)

```http
POST /api/v1/assignments
Authorization: Bearer <token>
Content-Type: application/json

{"student_id": 42, "locker_id": 17}
```

Успешный ответ: запись назначения с `assigned_at` и признаком active. Конфликт занятого/недоступного шкафчика должен вернуть документированную ошибку без изменения данных. Точный формат API установить по схемам приложения.
