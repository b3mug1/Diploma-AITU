# План верификации и оценки

## Вопрос оценки

Позволяет ли система корректно и быстрее поддерживать реестр и жизненный цикл назначения шкафчиков по сравнению с процессом, который реально использует выбранная образовательная организация?

## Базовый вариант и условия

Baseline — текущий реальный процесс (например, бумажный журнал или таблица), определить после согласия клиента. Нельзя заранее утверждать, что процесс ручной. Провести одинаковые сценарии на синтетических данных либо обезличенной выборке; зафиксировать размер выборки, роли участников, устройство, сеть, даты и процедуру измерения.

## Метрики

| Метрика | Способ измерения | Критерий/целевое значение |
|---|---|---|
| Успешность назначения | Доля сценариев, завершённых без ошибки участником | Установить после пилота с руководителем/клиентом |
| Время типового назначения | Время от начала сценария до подтверждения | Сравнить медиану системы и baseline; целевое снижение согласовать после baseline |
| Ошибки конфликтного назначения | Число созданных конфликтов при повторных/параллельных запросах | 0 конфликтных активных назначений в тестовом наборе |
| Корректность состояния реестра | Сверка ожидаемых и фактических статусов/счётчиков | 100% контрольных сценариев |
| Удовлетворённость/понятность | Короткая анкета после сценария и наблюдения | Заранее определить шкалу и интерпретацию; не делать вывод по малой выборке сверх её ограничений |
| Обновление dashboard | Задержка от commit события до отображения | Целевой порог определить после прототипа и условий теста |
| Корректность распределения | Сверить результат с заранее рассчитанным набором правил и tie-breaker | 100% соответствие принятой спецификации на контрольном наборе |
| Объяснимость распределения | Администраторы проверяют, может ли понять причину назначения для каждого результата | Целевой критерий согласовать; все решения должны иметь объяснение |
| Проверка распределения по группам | Сравнить доли получивших locker в разрешённых агрегированных категориях | Не задавать целевую пропорцию до согласования политики; анализировать отклонения и ограничения выборки |
| Жизненный цикл ремонта | Пройти заявку от подачи до закрытия/возврата; сверить переходы и аудит | 100% предусмотренных переходов проходят; недопустимые переходы блокируются |
| Время обработки ремонта | Измерять от подачи до назначения/закрытия на пилотных или синтетических данных | Порог/SLA установить после изучения текущего процесса |

## Тест-план

- Unit: проверки правил назначения, доступности и освобождения.
- Integration: API + БД, транзакции, ограничения уникальности, роли.
- Concurrency: два параллельных назначения одного шкафчика — успешно ровно одно.
- End-to-end: вход, поиск, назначение, просмотр студентом, освобождение, обслуживание.
- Allocation: приоритеты, tie-breaker, недостаток шкафчиков, неполные данные, повторный запуск, ручное изменение и объяснение результата.
- Repair workflow: подача студентом, назначение технику, выполнение, возврат/подтверждение, уведомление и запрет доступа к чужим заявкам.
- Негативные: невалидные ID/поля, дубликаты, запрещённая роль, недоступный шкафчик, повторное освобождение.
- WebSocket: событие отражено у подписанного клиента; проверка reconnect и авторизации.
- User testing: 3–5 представителей, только после получения согласия и без ненужных персональных данных.

## Отчётность

Хранить тестовые данные синтетическими; фиксировать commit/tag, окружение, сценарии, результаты, отклонения и ограничения. Любой численный результат приводить с условиями измерения и размером выборки.
