# Требования и критерии приёмки

**Версия:** начальная, подлежит проверке интервью. Приоритеты: Must — минимальный scope; Should — полезно, но не блокирует базовую демонстрацию.

| ID | Приоритет | Требование | Критерий приёмки / проверка | Источник |
|---|---|---|---|---|
| FR-01 | Must | Система аутентифицирует пользователя | Валидные учетные данные создают сессию/токен; неверные отклоняются без выдачи доступа | Проектное решение; подтвердить |
| FR-02 | Must | Система различает студента, администратора и техника | Каждая роль имеет только разрешённые операции; проверить endpoint и UI каждой роли | Проектное решение |
| FR-03 | Must | Администратор ведёт реестр студентов | Создание/просмотр/редактирование/поиск работают; barcode уникален, дубликат отклоняется | Проектное решение |
| FR-04 | Must | Администратор ведёт реестр шкафчиков и состояние | Создание/просмотр/редактирование состояния работают; уникальный номер проверяется | Проектное решение |
| FR-05 | Must | Администратор назначает доступный шкафчик студенту | Успешное назначение создаёт активную запись и отражается в запросах списка | Проектное решение |
| FR-06 | Must | Система предотвращает конфликт активных назначений | Нельзя назначить занятый/недоступный шкафчик; конфликтный запрос завершается контролируемой ошибкой | Проектное решение |
| FR-07 | Must | Администратор освобождает шкафчик | Активная запись получает дату освобождения; шкафчик становится доступным, если не на обслуживании | Проектное решение |
| FR-08 | Must | Пользователь видит только собственное назначение | User endpoint возвращает назначение текущего пользователя и не раскрывает данные других студентов | Проектное решение |
| FR-09 | Should | Система хранит историю назначений | Завершённое назначение остаётся доступно администратору с датами назначения/освобождения | Проектное решение |
| FR-10 | Should | Dashboard показывает агрегированные данные | Проверить подсчёты занятых, доступных и обслуживаемых шкафчиков на контрольном наборе | Проектное решение |
| FR-11 | Should | Dashboard получает обновления без ручной перезагрузки | После события назначения подключённый клиент отображает актуальное состояние в пределах установленного SLO | Проектное решение; определить SLO |
| FR-12 | Must | Система распределяет доступные шкафчики по утверждённому правилу приоритета | На фиксированном тестовом наборе выход соответствует опубликованным правилам; при равном приоритете применяется согласованный tie-breaker; администратор видит объяснение результата | Требует согласования с университетом |
| FR-13 | Must | Студент может создать заявку на ремонт своего шкафчика | Заявка содержит locker, категорию/описание проблемы и дату; студент не может подать заявку от имени другого пользователя | Проектное решение |
| FR-14 | Must | Администратор назначает заявку технику | Назначенный техник видит заявку в своей очереди; другой техник не получает право изменять её без разрешения | Проектное решение |
| FR-15 | Must | Техник отмечает выполнение ремонта | Система фиксирует исполнителя, время и результат; статус переходит в «ожидает подтверждения администратора» | Проектное решение |
| FR-16 | Must | Администратор подтверждает/возвращает завершённую заявку | Подтверждение закрывает заявку и формирует уведомление студенту; возврат требует комментария и снова отображается технику | Проектное решение |
| FR-17 | Should | Система показывает статус ремонта студенту | Студент видит только собственную заявку и понятный статус/обновление | Проектное решение |

## Нефункциональные требования

| ID | Приоритет | Требование | Проверка |
|---|---|---|---|
| NFR-01 | Must | Доступ к административным операциям защищён авторизацией на сервере | Интеграционные тесты для каждой защищённой группы endpoint |
| NFR-02 | Must | Персональные данные выдаются только уполномоченным ролям и только в необходимом объёме | Тесты доступа и ревью схем API; не использовать реальные данные в демо |
| NFR-03 | Must | Ограничения назначения устойчивы к параллельным запросам | Одновременные назначения одного шкафа: ровно одно успешно; проверить транзакцией/ограничением БД |
| NFR-04 | Should | Ключевые экраны понятны целевым пользователям | Сценарное тестирование с 3–5 представителями; фиксировать завершение и замечания |
| NFR-05 | Should | Ошибки валидации объясняют, что исправить | Проверка UI/API на пустые, некорректные и дублирующиеся значения |
| NFR-06 | Should | Операции имеют историю для аудита | Проверить наличие автора, действия, объекта и времени для согласованных событий |
| NFR-07 | Must | Результат автоматического распределения объясним и проверяем | Для каждого назначения администратор видит применённое правило/приоритет и причину выбора; результат воспроизводится на тех же входных данных |
| NFR-08 | Must | Данные социального статуса, активности и GPA минимизированы и защищены | Не собирать их до утверждения необходимости/правового основания; доступ ограничен; журналы и экспорт не раскрывают эти поля без разрешения |
| NFR-09 | Should | Заявки на ремонт имеют конечный и аудируемый жизненный цикл | Нельзя закрыть заявку без результата; переходы статусов и ответственные фиксируются |

## Вопросы, требующие решения

- Разрешено ли студенту самому выбрать/запросить шкафчик или назначает только администратор?
- Может ли студент иметь несколько шкафчиков; могут ли шкафчики быть общими?
- Какие статусы/размеры/access type нужны, и что означает `capacity`?
- Как официально определяются приоритетные категории, активность и порог GPA? Кто утверждает правила и кто проверяет исходные данные?
- Есть ли правовое и организационное основание хранить социальный статус, GPA и активность? Может ли распределение обойтись подтверждением права на приоритет без хранения причины?
- Каков порядок апелляции, ручного переопределения и разрешения равных приоритетов?
- Какие категории проблем ремонта и сроки обработки (SLA) нужны; кто может менять статус и уведомлять студента?
- Какие правила срока назначения, просрочки, потери доступа и обслуживания?
- Какие языки обязательны и какой минимальный уровень доступности нужен?
